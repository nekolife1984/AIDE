# レビュールール

## 指摘の基準

- 変更範囲内の不具合、要件未達、セキュリティ問題、重要な検証漏れを優先。
- 実害・根拠・対応案を示せる指摘に限定。推測、好み、軽微な書式、範囲外の改善は指摘しない。
- 同じ内容を重複して指摘しない。問題箇所と影響を具体的に記載する。

## 利用文脈

利用文脈は、変更の想定ユーザー（個人・特定多数・不特定多数など）、動作環境（ローカル限定・外部アクセスありなど）、必要に応じて扱うデータの性質を指す。レビュー依頼者はこれらを依頼時に明示し、レビュアーは実際の影響範囲と利用文脈に照らしてレビュー水準と重要度を判定する。不明な場合は確認し、推測で安全と決めつけない。個人情報・認証情報・金銭に関するデータや法規制が絡む事項を扱う変更では、データの性質を必ず明示する。

個人情報・認証情報・金銭に関するデータや法規制が絡む事項は、個人・ローカル限定でも水準を下げない。この下限は、以下の緩和の目安より優先する。

- 個人・ローカル限定で、本人と本人のデータの範囲で完結する脅威は、原則として必須にしない。ただし、要件や実際の影響によっては必須になり得る。
- 不特定多数・外部アクセスありでは、第三者への影響や攻撃可能性を厳格に見る。
- 組み合わせやデータの機密性、第三者への影響も考慮し、分類だけで一律に判断しない。
- 前提条件の現実味：通常利用で起こるか、意図的に作らないと起きないかを見て、強い権限や特殊な状態を要する場合は実害を小さく見積もる。
- 影響の可逆性：履歴・バックアップ・再生成で回復できるか、外部への送信・課金・削除・公開などで不可逆かを見て、不可逆な影響は厳格に見る。
- 既存の緩和策：OSやプラットフォームなど他の層で既に止まっているかを見て、単体の弱さだけで実害と判断しない。

## 指摘の区分

- **必須**：修正しないと正しさ・安全性・完了条件を損なうもの。マージ前の対応対象。
- **提案**：任意の改善。採用は作者の判断。

## 指摘への対応

- 提案は作者が採否を判断する。不採用理由は、PR作成前の独立レビューではIssueコメントに、PR上の指摘ではPRに記録する。
- 必須指摘への異議は根拠を示して確認し、合意または責任者の最終判断まで未解決として扱う。利用文脈に照らして過剰と判断した必須指摘は、合意または責任者の最終判断の後、理由を記録して「採用せず」として閉じられる。単に対応コストが高いだけでは拒否しない。
- 不採用の記録はPR作成前の独立レビューではIssueコメント、PR上の指摘ではPRに残す。指摘を特定し、`利用文脈／想定される影響／過剰と判断した理由／判断者・合意／状態：採用せず`を記載する。独立レビューの既存記録は書き換えず、対応結果を追記する。文脈が変わった場合は不採用の指摘を再評価し、結果を同じ追跡先に記録する。試作から本番への移行も文脈の変更として扱う。
- 修正した指摘は変更内容と確認結果を返信する。

## PR作成前の独立レビュー

開発変更では、ローカル検証後、PRを作成する前に実装者とは独立したレビュアーが最終差分を確認する。依頼にはIssueの受け入れ条件、レビュー対象の差分と次の利用文脈欄を明示し、未確認の変更を含めない。

```markdown
- 利用文脈：想定ユーザー <対象>; 動作環境 <環境>; データの性質 <必要に応じて記載／該当なし。個人情報等を扱う場合は必須>
```

- 指摘は[指摘の区分](#指摘の区分)に従い、必須と提案を分ける。
- 実行環境で独立レビュー用のサブエージェントまたは外部レビューツールを利用できる場合は、利用者から別途指示がなくても、その手段へレビューを依頼する。実装者自身が同じ作業の中で差分を読み返すだけの自己レビューは、独立レビューとして扱わない。
- 独立したレビュアーへ依頼できる手段がない場合は、レビュー未実施としてPR作成を止め、利用できない理由と必要な対応を報告する。
- 必須指摘はPR作成前に修正・検証する。利用文脈に照らして過剰な場合を含む異議と不採用は[指摘への対応](#指摘への対応)に従い、解決までPR作成を保留する。提案は作者が採否を決め、採用しない場合は理由を記録する。
- 指摘対応で差分が変わった場合は、変更後の最終差分を新しいレビューで確認する。過去のレビュー結果を流用しない。
- レビュー未実施、応答なし、失敗、タイムアウトは合格とみなさない。
- レビュー結果は次節の形式でIssueに記録してから指摘対応を始める。

## 独立レビュー結果の記録

独立レビューとは、実装者とは別の担当者・エージェント等が対象変更を確認することを指す。GitHubのPRレビュー、外部ツールなど手段・担当者を問わず、対象Issueのレビュー結果はIssueコメントで追跡する。

レビュー完了後、指摘の有無を問わず、指摘への対応を始める前に記録する。同一Revisionを同一ラウンドで複数の手段・担当者が確認した結果は、1コメントにまとめてよい。レビュー対象はbaseとheadの完全なSHAで固定し、レビュー担当が取得したremote refまたは成果物も記録する。未コミット差分を対象にする場合は、base SHA、対象ファイル、差分のSHA-256、レビュアーが同じ差分を取得した方法を記録する。ローカルパスやブランチ名だけで対象を特定せず、レビュアーが差分へアクセスできない場合はレビュー未完了とする。修正後の再レビューは、新しい対象Revisionを明記してIssueコメントへ追記する。過去の記録は書き換えない。

PRレビューに既に記録された指摘はIssueへ転載しない。同一指摘を独立レビューでも確認した場合、IssueにはPRレビューへのリンクと対応状況だけを記録する。

```markdown
## 独立レビュー（YYYY-MM-DD）
- 対象：`OWNER/REPO`; PR #<番号> またはブランチ `<名前>`; base `<完全なSHA>`; head `<完全なSHA>`
- 取得元：<レビュー担当が確認したremote refまたは共有済み成果物>
- 利用文脈：想定ユーザー <対象>; 動作環境 <環境>; データの性質 <必要に応じて記載／該当なし。個人情報等を扱う場合は必須>
- 未コミット差分の場合：base `<SHA>`; 対象ファイル `<相対パス>`; diff SHA-256 `<値>`; 取得方法 `<説明>`
- 種別：<初回／再レビュー>
- 手段・担当：<レビュー方法・担当者（分かる範囲で）>
- 判定：<指摘なし／必須指摘あり／提案のみ／保留>
- 指摘：
  - <必須／提案> `<path:line>` — <要約> — 状態：<未対応／対応中／修正済み／採用せず（理由）>
  - <指摘がない場合は「なし」>
- PR上の関連指摘：<レビューURLと対応状況、またはなし>
- 未解決点：<内容、またはなし>
```

レビュー本文・プロンプト・生ログ、秘密情報、個人情報は転載せず、追跡に必要な要約だけを記録する。機密の脆弱性情報は[情報保護](06-security.md)に従い、Issueへ記載しない。
