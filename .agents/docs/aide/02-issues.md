# イシュー管理

## AIによるコメント

AIがIssueまたはPRにコメントを追加する場合は、コメントの冒頭に次の表示を付ける。

```markdown
> 🤖 AIアシスタントによるコメント
```

このルールの対象はIssue・PRへのコメント追加のみとし、Issue本文・PR本文などには適用しない。人間による確認状況の表示は設けない。

## 起票

- Issue・コメント・PRは日本語で記載。
- 1 Issueは1つの目的に絞り、独立した作業は分割。依存関係を明記する。
- 重複Issueは新規作成せず、既存Issueを更新。
- 作成したIssueはGitHub Projectへ登録し、`Backlog`に設定。
- タイトルは短く具体的に。種別を付ける場合は `機能:`、`修正:`、`文書:`、`保守:`。

### 重複確認

新規Issueの作成前に、依頼の目的・対象領域・主要な機能名から2〜4個の検索語を選ぶ。同義語や略称があれば別の検索語として加える。

```bash
gh issue list --repo OWNER/REPO --state all --search "<検索語1>" --limit 100
gh issue list --repo OWNER/REPO --state all --search "<検索語2>" --limit 100
gh issue list --repo OWNER/REPO --state all --search "<同義語または関連語>" --limit 100
```

検索語または短い語句を個別に検索する。結果が広すぎる場合は、より具体的な語句で絞り直す。検索結果から関連候補だけを選び、その本文・状態・関連PRを確認する。全Issueを順番に読む必要はない。

- OPENの候補が同じ目的なら、新規作成せず既存Issueの更新を検討する。別スコープの作業なら新規Issueに分け、関連Issueを参照する。
- CLOSEDの候補は完了理由や関連PRを確認する。同じ対応が完了済みなら再起票しない。未完了の同一目的なら既存Issueの再オープン・更新を検討する。別スコープの未完了作業だけを新規Issueにし、関連Issueを参照する。
- 2〜4個の検索語で関連候補が見つからなければ、新規Issueを作成できる。

## 本文

完了条件は検証可能な形で記載し、条件ごとの確認方法を定める。[完了条件・検証基準](05-quality.md)を参照。

```markdown
## 目的
<背景と目的>

## 対応
<変更内容>

## 完了条件
- [ ] <検証可能な条件>

## 依存・参考
<関連Issue・資料。なければ「なし」>
```

不具合Issueには再現手順・期待結果・実際の結果を記載。

## 着手・完了

- 変更前にIssueを作成し、内容を確認。
- Issue作成のみの依頼は、確認と着手許可を待つ。実装まで依頼された場合は追加確認不要。
- PRからIssueを参照し、完了条件の検証とマージ後にIssueを閉じる。

## 作業中の進捗記録

作業を続ける間は、再開に役立つ節目でIssueコメントを追加する。

- 設計・方針が固まったとき
- 実装や検証のまとまりが完了したとき
- ブロッカーが発生・解消したとき
- 作業を中断するときは、次の「中断・再開」の形式を使う

コマンドやファイルごとの逐次投稿はせず、同じ工程の細かな作業はまとめる。状況に変化がなく、再開に役立たない繰り返し更新も避ける。

```markdown
## 進捗（YYYY-MM-DD）
- Repository：`OWNER/REPO`; ブランチ `<名前>`
- 対象Revision：base `<SHA>` → head `<SHAまたは未コミット>`
- 完了：<完了した作業>
- 変更箇所・状態：<リポジトリ相対パス>; コミット `<SHAまたは未コミット>`; push `<済／未>`
- 引き継ぎ可能性：<別環境から取得可能／現環境のみ>; <remote ref・PR・共有済み成果物、または取得できない理由>
- 検証：`<実行内容>` — <実際の結果>
- 未解決点・ブロッカー：<内容またはなし>
- 次の作業：<次に行うこと>
```

リポジトリ相対パスで対象を示し、ローカルworktreeの絶対パスだけを取得方法として記載しない。未コミット変更は、別環境から取得可能かと具体的な受け渡し元を明記する。取得できない場合はその制約をブロッカーとして残し、次の作業で解消するまで引き継ぎ済みと扱わない。

進捗記録は作業継続中の節目を残すもの。中断時の再開メモは引き継ぎ用であり、同じ中断について両方を重複投稿しない。

## 中断・再開

中断時はIssueを開いたまま、Projectを `In progress` に保つ。Issueコメントに次の再開メモを残す。

```markdown
## 再開メモ（YYYY-MM-DD）
- Repository：`OWNER/REPO`; ブランチ `<名前>`; base `<SHA>`; head `<SHAまたは未コミット>`
- 変更箇所・状態：<リポジトリ相対パス>; コミット `<SHAまたは未コミット>`; push `<済／未>`
- 引き継ぎ元：<別環境から取得できるremote ref・PR・共有済み成果物、または現環境のみで取得不可>
- 検証済み：実行内容と結果
- 未解決点・ブロッカー：
- 次の作業：
```

再開時はIssue本文・最新コメント・Project StatusとRepositoryのremoteを確認し、対象ブランチ・base/head・作業ツリーと未追跡ファイルを読み戻す。ignoredファイルは引き継ぎに関係する場合に限って確認する。コメントのRevision・変更ファイル・取得元が現状と一致することを確かめてから作業する。不一致、未コミット差分の取得不能、所有者不明の変更があれば上書き・破棄せず、状態を整理してIssueへ記録する。

### 引き継ぎ可能性の確認

中断時とPR作成前に、最新コメントと受け渡し可能なRepository状態だけを見た別エージェントが、次を判断できるか確認する。

- 開始するRepository・ブランチ・base/head Revisionを特定できる。
- 対象の変更を取得でき、未コミット変更・未追跡ファイルの有無と引き継ぎ方法が分かる。
- 実行済み検証と実際の結果、未解決点、次の具体的な作業が分かる。

判断に必要な情報や変更へのアクセスが欠けていれば引き継ぎ完了とせず、不足点をコメントと次の作業へ記載する。差分全文・ログ・秘密情報をIssueへ転載しない。
