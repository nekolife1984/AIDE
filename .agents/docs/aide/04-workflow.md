# Issue・Project開発フロー

```text
Issue作成・Project登録（Backlog）
→ 着手許可・Ready
→ 実装・検証（In progress）
→ PR作成前の独立レビュー ↔ 指摘対応・再レビュー
→ 完了条件の確認・チェック
→ PR（In review）↔ 修正（In progress）
→ マージ前のPR指摘確認
→ 完了記録・Issue完了・Done
```

## 依頼範囲の確認

- 作業開始前に、依頼がどの工程までを求めているか確認する。終了境界が明示されていればその範囲まで進み、先の工程へ進まない。
- 終了境界が未指定または曖昧なら、Issue作成・Project登録まで／実装・検証・PR提出まで／PRのマージとIssue・Projectの完了まで、などの選択肢を示してユーザーに確認する。回答までは、Issue・Projectの更新、ブランチ作成、実装、PR作成、マージなど範囲に依存する操作を行わない。確認に必要な読み取り専用の調査は行ってよい。
- 「Issueにして」はIssue作成・Project登録までとして扱い、実装には別途着手許可を要する。「実装してPRまで」など境界が明示されていれば、その範囲について追加確認しない。PR提出はマージ・Issue完了の許可を含まない。

1. Issueを作成し、Projectへ `Backlog` 登録。詳細は[イシュー管理](02-issues.md)を参照。
2. Issue作成のみの依頼は着手許可を待つ。依頼範囲の確認は上記「依頼範囲の確認」に従う。着手が許可され、依存解決済みなら `Ready`。作業開始時に `In progress`。
3. ブランチ戦略に従って実装・検証し、PR作成前に、実装者とは独立したレビュアーが最終差分を確認する。必須指摘は修正・検証し、異議がある場合は合意または責任者の判断を得る。指摘対応で差分が変わった場合は最終差分を再レビューし、未解決の必須指摘がないことを確認する。最終レビュー後、PR作成前にIssue本文の完了条件を一項目ずつ差分・検証結果などの根拠と照合し、達成を確認できた項目だけを `[x]` にする。未達・未検証の項目は未チェックのまま対応・再検証する。完了条件を満たすための修正で差分が変わった場合は、変更後の最終差分を独立レビューし、その後に全完了条件を改めて根拠と照合してチェック状態を更新する。未達・未検証が残る場合はこの確認を繰り返し、すべての完了条件を確認できるまでPRを作成しない。チェック更新後はIssue本文を読み戻す。設計・実装・検証・レビューの節目でIssueへ進捗を記録する。詳細は[イシュー管理](02-issues.md)と[レビュールール](07-review.md)を参照し、PRからIssueを参照する。検証基準は[完了条件・検証基準](05-quality.md)を参照。
4. PR作成後は `In review`。修正時は `In progress` に戻し、再確認時に `In review`。
5. マージと完了条件を確認し、Issueを閉じてProjectを `Done` にする。PR・Issue・Projectの状態を読み戻した後、結果をIssueの完了コメントへ記録する。

## PR本文

PR本文は、Issueを知らない読み手にも変更の理由・範囲・確認結果が分かるよう、日本語で具体的に書く。Issueの完了条件全文は複製せず、Issue番号で参照する。次の構成を基本とし、該当しない項目は「なし」または理由を記載する。

```markdown
## 概要
Issue #<番号>に対応し、<実現した状態>にします。

## 変更内容
- <変更した対象と具体的な変更>

## 検証
- `<実行したコマンドまたは操作>` — <実際の結果>
- CI：<チェック名と状態／未設定／未実行と理由>

## リスク・残課題
- <影響・制約・残作業。なければ「なし」>

## 関連Issue
Closes #<番号>
```

「改善しました」「確認しました」だけで終わらせず、対象・結果・根拠を示す。例えば「設定画面を改善する」ではなく「保存後に設定を読み直し、画面を開き直しても同じ値が表示されることを確認した」と書く。未実施の検証は実施済みと混同せず、理由と残作業を記載する。変更の背景や受け入れ条件はIssueを参照し、PRには実際の差分・検証・リスクを記載する。

PR作成前の独立レビュー結果は、PR本文に代用・転記せず、[レビュールール](07-review.md#独立レビュー結果の記録)に従ってIssueへ記録する。レビュー結果の公開後にPRを作成し、Project Statusを更新する。

## レビュー指摘

指摘の基準と異議への対応は[レビュールール](07-review.md)を参照。

- コード箇所はPRのインラインコメント、全体所見はPR総評に記録。
- 独立レビューの結果はIssueコメントで追跡する。PRレビューのインライン指摘・総評に詳細がある場合は重複転記せず、該当レビューへのリンクと対応状況を記録する。形式は[レビュールール](07-review.md)を参照。
- マージ前の必須修正は同じPRで対応。
- マージ前にPR上の最新レビュー・レビューコメント・未解決スレッドを読み戻す。必須指摘は修正し、提案は採否と理由を説明する。未対応の変更要求、未解決のスレッド、残作業がないことを確認してからマージする。
- 別途対応する改善はIssue化し、Projectの `Backlog` に登録してPRから参照。
- 中断時は再開に必要な情報のみIssueへ記録。

## 中断

Issueを開いたままProjectを `In progress` にし、引き継ぎ情報をIssueコメントに残す。形式は[イシュー管理](02-issues.md)を参照。

## 完了時の記録

マージ後、Issueを閉じてProjectを `Done` にした状態を読み戻し、Issueへ最終コメントを残す。CIが未設定・未実行の場合は成功と混同せず、別々に記録する。

```markdown
## 完了（YYYY-MM-DD）
- 成果：PR <URL>; マージコミット `<SHA>`
- 状態確認：Issue #<番号> `<Closed>`; Project `<名前>` `<Done>`
- 検証：`<実行コマンド>` — <実際の結果>
- CI：<チェック名と実際の状態／未設定／未実行と理由>
- 残作業：<なし／関連Issueと次の対応>
```

最終コメントと読み戻したRepository状態だけで、変更成果・完了根拠・未完了作業を別エージェントが判断できることを確認する。詳しい確認項目は[イシュー管理](02-issues.md)の「引き継ぎ可能性の確認」を参照。
