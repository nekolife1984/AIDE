# イシュー管理

## 起票

- Issue・コメント・PRは日本語で記載。
- 1 Issueは1つの目的に絞り、独立した作業は分割。依存関係を明記する。
- 重複Issueは新規作成せず、既存Issueを更新。
- 作成したIssueはGitHub Projectへ登録し、`Backlog`に設定。
- タイトルは短く具体的に。種別を付ける場合は `機能:`、`修正:`、`文書:`、`保守:`。

### 重複確認

新規Issueの作成前に、依頼の目的・対象領域・主要な機能名から2〜4個の検索語を選ぶ。同義語や略称があれば別の検索語として加える。

```bash
gh issue list --repo OWNER/REPO --state all --search "<検索語1>" --limit 100
gh issue list --repo OWNER/REPO --state all --search "<検索語2>" --limit 100
gh issue list --repo OWNER/REPO --state all --search "<同義語または関連語>" --limit 100
```

検索語または短い語句を個別に検索する。結果が広すぎる場合は、より具体的な語句で絞り直す。検索結果から関連候補だけを選び、その本文・状態・関連PRを確認する。全Issueを順番に読む必要はない。

- OPENの候補が同じ目的なら、新規作成せず既存Issueの更新を検討する。別スコープの作業なら新規Issueに分け、関連Issueを参照する。
- CLOSEDの候補は完了理由や関連PRを確認する。同じ対応が完了済みなら再起票しない。未完了の同一目的なら既存Issueの再オープン・更新を検討する。別スコープの未完了作業だけを新規Issueにし、関連Issueを参照する。
- 2〜4個の検索語で関連候補が見つからなければ、新規Issueを作成できる。

## 本文

完了条件は検証可能な形で記載し、条件ごとの確認方法を定める。[完了条件・検証基準](05-quality.md)を参照。

```markdown
## 目的
<背景と目的>

## 対応
<変更内容>

## 完了条件
- [ ] <検証可能な条件>

## 依存・参考
<関連Issue・資料。なければ「なし」>
```

不具合Issueには再現手順・期待結果・実際の結果を記載。

## 着手・完了

- 変更前にIssueを作成し、内容を確認。
- Issue作成のみの依頼は、確認と着手許可を待つ。実装まで依頼された場合は追加確認不要。
- PRからIssueを参照し、完了条件の検証とマージ後にIssueを閉じる。

## 作業中の進捗記録

作業を続ける間は、再開に役立つ節目でIssueコメントを追加する。

- 設計・方針が固まったとき
- 実装や検証のまとまりが完了したとき
- ブロッカーが発生・解消したとき
- 作業を中断するときは、次の「中断・再開」の形式を使う

コマンドやファイルごとの逐次投稿はせず、同じ工程の細かな作業はまとめる。状況に変化がなく、再開に役立たない繰り返し更新も避ける。

```markdown
## 進捗（YYYY-MM-DD）
- 完了：<完了した作業>
- 変更箇所・状態：<パス>; ブランチ `<名前>`; コミット `<SHAまたは未コミット>`
- 検証：`<実行内容>` — <実際の結果>
- 未解決点・ブロッカー：<内容またはなし>
- 次の作業：<次に行うこと>
```

進捗記録は作業継続中の節目を残すもの。中断時の再開メモは引き継ぎ用であり、同じ中断について両方を重複投稿しない。

## 中断・再開

中断時はIssueを開いたまま、Projectを `In progress` に保つ。Issueコメントに次の再開メモを残す。

```markdown
## 再開メモ（YYYY-MM-DD）
- 進捗・変更箇所：ブランチ、コミット、未コミットのファイル
- 検証済み：実行内容と結果
- 未解決点・ブロッカー：
- 次の作業：
```

再開時はIssue・最新コメント・Project Status・ブランチ・作業ツリーを確認。会話履歴だけに頼らない。
